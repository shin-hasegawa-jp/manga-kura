# 重複画像検出

## 現行の保存順

1. 保存画面で同一の元ページURLを警告する。
2. 選択画像を画像プロキシ経由でBlobとして取得する。
3. Blobと寸法から登録画像モデルを生成する。
4. 作品・話・画像を1つのIndexedDBトランザクションで登録する。

## 変更範囲

- BlobのSHA-256ハッシュ生成とURL正規化
- 画像モデルへの任意の内容ハッシュ追加
- 同一バッチ内およびIndexedDB保存済み画像との重複判定
- 重複先の作品・話・画像位置を示す保存前警告

## 方針

- URL一致と画像内容一致は別の根拠として表示する。
- 画像内容はWeb Crypto APIだけで処理し、外部へ送信しない。
- 既存画像のハッシュは一括移行せず、比較時に必要なBlobだけを順次計算する。
- URL重複警告を先に確認し、その後に画像を取得して画像重複を警告する。
- 重複画像の保存を自動禁止せず、明示操作があった場合だけ継続する。
- 既存画像の上書き、統合、自動削除は行わない。

## 品質確認

- Frontend：`format`、`lint`、`type-check`、`test:unit`が成功（49 files / 299 tests passed）
- Frontend：本番ビルドとPWA生成が成功
- 100件の新規画像と100件の保存済み画像を逐次比較するテストは30msで完了
- 保存済み画像は主キーを先に取得し、Blobを含むレコードを1件ずつ読み込むため、全Blobを同時にメモリへ展開しない
- 新規作品、既存作品への話追加、単独の話は共通の保存処理を通り、各モードの既存登録テストと重複警告前後の保存テストが成功
- 重複警告時は登録処理を開始せず、明示保存時だけハッシュ付き画像を登録することを確認
- 実サイトで初回保存、続けて保存、URL重複警告が画像取得より先に表示されること、入力と選択が保持されることを確認

実サイトの2回目の画像取得では、既知の画像プロキシ上流エラー（HTTP 400/502）が発生した。画像重複警告自体は取得済みBlobを用いた結合テストで確認し、取得失敗時に不完全な登録を残さない既存動作も確認した。

## レビュー構成

1. 任意の内容ハッシュとIndexedDB v2の互換移行
2. 同一バッチ・保存済み画像の逐次重複判定
3. URL警告後に表示する画像重複警告と明示保存
4. 自動テスト、性能確認、実サイト確認

レビューでは、URL一致と内容一致を区別すること、既存画像を一括変換しないこと、警告を明示的に承認するまで登録処理を開始しないことを重点的に確認する。
