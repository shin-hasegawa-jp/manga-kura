# 保存フロー性能調査

## 現行フロー

### プレビュー

1. `SaveView.vue`が`analyzePageImages`を呼び出す
2. Frontendが`POST /v1/pages/analyze`へ対象ページURLを送る
3. APIがHTMLを取得し、画像候補を抽出してプレビュー用・保存用トークンを発行する
4. Frontendが各候補のプレビュー用トークンで`GET /v1/images/proxy`を呼び出す
5. APIが取得元画像をストリーミングし、ブラウザが候補カードへ表示する

### 保存

1. `SaveView.vue`が選択候補と登録情報を`saveAnalyzedPage`へ渡す
2. `imageBlobClient.ts`が各候補の保存用トークンで`GET /v1/images/proxy`を呼び出す
3. APIが取得元画像をストリーミングする
4. FrontendがレスポンスをBlob化し、不足している画像寸法を取得する
5. `registrationService.ts`が作品・話・画像を1つのIndexedDBトランザクションで登録する

## 責務と主な確認箇所

| 区間 | 責務 | 主な実装 |
|---|---|---|
| HTML取得・候補抽出 | API | `page_html_fetcher.py`、`page_analyzer.py` |
| 取得元へのアクセス間隔 | API | `rate_limiter.py`、`external_http_client.py` |
| 画像ストリーミング・上限検査 | API | `image_proxy.py`、`proxy_usage_tracker.py` |
| プレビュー要求・表示 | Frontend | `SaveView.vue`、`acquisitionApiClient.ts` |
| 保存画像の取得・Blob化 | Frontend | `imageBlobClient.ts`、`saveAnalyzedPage.ts` |
| IndexedDB登録 | Frontend | `registrationService.ts`、`repository.ts` |

## 維持する制約

- APIへURL、HTML、画像、トークンを永続保存しない
- SSRF対策、リダイレクト検査、画像件数・単体サイズ・合計サイズ制限を維持する
- 取得元ドメインへのアクセス間隔を維持し、瞬間的な過負荷を避ける
- 画像取得が一部でも失敗した場合は登録を開始せず、再試行時は取得済み画像を再利用する
- 作品・話・画像のIndexedDB登録は同一トランザクションで行う

## 調査の進め方

少数画像（3件）と多数画像（20件）を同じ取得元・同じ通信条件で各3回実行し、中央値を比較する。ブラウザではページ解析、先頭プレビュー、主要プレビュー、全プレビュー、保存画像取得、IndexedDB登録を分ける。APIでは取得元アクセス間隔の待機とレスポンスのストリーミングを分け、取得元やネットワーク由来の時間をアプリ内部処理と混同しない。

## 変更前の基準

2026-07-24時点のコードと自動テスト用の遅延レスポンスから、アプリ内部の直列化箇所を次のとおり特定した。実サイトの秒数は取得元と回線に左右されるため、Pull Requestの動作確認時に後述の記録表を埋める。

| 区間 | 変更前の動作 | 待ち時間への影響 |
|---|---|---|
| プレビュー | 全候補の`img`を一度に生成し、画面外も即時取得 | 候補数が多いと初期候補と画面外候補が帯域を奪い合う |
| 保存画像取得 | `for`ループ内で1件ずつ`await` | N件の取得時間がほぼ加算される |
| APIドメイン間隔 | 共通ロックを保持したまま同一ドメインの間隔を待つ | あるドメインの待機中、別ドメインの要求開始も止まる |
| IndexedDB画像登録 | 同一トランザクション内で1件ずつ`put` | N件分の非同期要求を逐次待機する |

保存画像取得の制御テストでは、遅延する取得処理の最大同時実行数が`1`になることを変更前の基準とする。APIの制御テストでは、同一ドメインの開始間隔が設定値以上であることに加え、別ドメインがその待機に巻き込まれるかを基準とする。

## 手動計測手順

1. APIとFrontendを開発モードで起動し、ブラウザのキャッシュを無効にする
2. DevToolsのNetworkで`/v1/pages/analyze`と`/v1/images/proxy`だけを表示する
3. URL解析を開始し、解析完了、先頭候補表示、画面内候補表示、全候補表示の時刻を記録する
4. 選択数を記録して保存を開始し、最後の画像レスポンス完了と保存完了画面の時刻を記録する
5. API側では同時刻の要求について、取得元ホスト、間隔待機、レスポンスヘッダー到着、ストリーム完了を確認する
6. 少数画像・多数画像を各3回実行し、外れ値ではなく中央値を比較する

URL、プロキシトークン、画像内容はログやPull Requestへ記録しない。取得元は「同一ドメイン」「複数ドメイン」のように匿名化する。

## API側の切り分け結果

画像プロキシはレスポンスを全件バッファリングせず、取得元から受け取ったチャンクをそのまま返している。単体サイズ・合計サイズもストリーミング中に検査されており、この区間に不要な直列処理は確認されなかった。

一方、取得元へのアクセス間隔を守る`DomainAccessLimiter`は、同一ドメインの次回アクセスまでスリープしている間も全ドメイン共通のロックを保持していた。このため、別ドメインの画像まで待機に巻き込まれていた。アクセス開始枠をロック内で予約し、実際の待機をロック外へ移した。同一ドメインの開始間隔は維持しつつ、無関係なドメインは独立して開始できる。

## プレビュー側の切り分け結果

候補カードは候補数にかかわらず全画像のURLを一度に設定していた。多数画像では画面外の候補も初期候補と同時に取得を始め、接続枠と帯域を奪い合う。先頭6件は即時読み込み、先頭2件は高優先度とし、7件目以降はブラウザ標準の遅延読み込みへ変更した。画像のデコードも非同期とし、選択状態や取得エラーの扱いは変更しない。

## 保存側の切り分け結果

保存画像は1件の取得が完了するまで次の取得を始めない完全な逐次処理だった。取得元へのアクセス間隔はAPIが制御しているため、Frontendは最大4件のワーカーで取得する方式へ変更した。結果は候補順へ戻してから登録し、失敗候補と取得済み画像のキャッシュも従来どおり維持する。保存画面には、並行処理でも実態が分かるよう処理済み件数を表示する。

IndexedDBは作品・話・画像を同一トランザクションへまとめていたが、画像だけは1件ずつ`put`して完了を待っていた。各画像を従来どおり検証した後、Dexieの`bulkPut`で一括登録する。トランザクションの原子性と、一部取得失敗時に登録を開始しない仕様は変更しない。

## 変更後の確認結果

2026-07-24に自動テストの制御可能な遅延処理で、次の構造的な改善を確認した。実サイトの絶対時間は取得元・画像サイズ・通信環境に依存するため、匿名化した実サイトでの秒数はDraft Pull Requestのブラウザ確認時に「手動計測記録」へ追記する。

| 確認項目 | 変更前 | 変更後 |
|---|---:|---:|
| 保存画像取得の最大同時実行数 | 1 | 4 |
| 6件取得時の処理波数 | 6 | 2 |
| 20件取得時の処理波数 | 20 | 5 |
| 別ドメインへのAPIアクセス | 同一ドメインの待機ロックに巻き込まれる | 独立して開始 |
| 同一ドメインの開始間隔 | 設定値以上 | 設定値以上を維持 |
| 1登録あたりの画像書き込み要求 | 画像件数分の`put` | 1回の`bulkPut` |

取得失敗を含む結果でも元の候補順を維持し、成功画像と失敗候補を分離することを単体テストで確認した。一部失敗時は`saveAnalyzedPage`が登録処理を呼ばないため、不完全な作品・話・画像は保存されない。既に取得できた画像は再試行用キャッシュへ残る。
